# Service SEO and provider architecture — 26 October 2026

Source assessment of the current PHP implementation; no live site, search engine, Search Console, competitor or Hostinger was contacted. This follows the owner's earlier no-website-contact restriction. Keyword demand and ranking opportunities below are hypotheses, not measured volumes or forecasts.

## Decision

Improve the existing 17 service pages before expanding the catalog. Keep all 39 current URLs. The services already cover evaluation, vulnerability assessment, authorized pentesting, accounts/cloud/endpoints, backup, incident preparation/response, training, governance, ISO, PCI, privacy, SOC and CISO work. New near-duplicate pages would increase maintenance without necessarily answering a different need.

The earlier release added relationships, worksheets and illustrative acceptance criteria. The next editorial pass should add service-specific depth and evidence, not repeat generic sections or target a word count. The mega menu improves discovery and uses real server-rendered links; it does not itself establish relevance, expertise, demand or ranking improvement.

## Page-level SEO work, in order

1. Map each URL to one primary intent plus supporting questions using Search Console data. Separate broad evaluation, vulnerability assessment and pentesting so they do not all answer the same generic query.
2. Prepare natural Paraguay-specific title/snippet candidates for priority pages. Test in small batches after recording a baseline; do not append cities/keywords to every heading or change stable URLs.
3. Expand answers that materially help a buyer choose scope: who it suits, when it is the wrong service, process, dependencies, deliverables, acceptance, exclusions and what happens after delivery.
4. Add a few genuine service-specific FAQs, answered visibly. Avoid repeating generic questions across all pages or treating FAQ markup as a ranking shortcut.
5. Add illustrative, clearly labeled result samples and comparison records. Real anonymized reports/cases require permission and review; never invent customers or outcomes.
6. Obtain actual technical reviewer identity, competence and dated review for relevant pages. Do not turn pending labels into approved claims without review.
7. Keep contextual service/guide links; add links only where they answer the next question. All 17 menu links must stay crawlable HTML anchors, not JS-only navigation.
8. Retain stable canonicals, redirects, sitemap and indexation during the editorial pass. Check HTML status, mobile layout and page metadata on every changed URL.
9. Validate performance with the actually deployed fonts/media; maintain readable fallback, reduced-motion/save-data handling and an accessible menu. Local blocked-asset tests do not prove live Core Web Vitals.
10. Measure landing-page impressions/clicks/CTR and qualified accepted enquiries. Current analytics records intent; successful delivery must be verified separately in private receipts/outbox. Do not infer enquiry conversion from thank-you views.

Authoritative sources should be checked during an authorized web-research/technical review pass. Existing source links do not prove new interpretations are current. No new legal or standards advice is approved by this plan.

## Why Proveedores exists

Servicios answers: what work should I buy, and what should its scope contain?
Proveedores should answer: whom can I hire, what can be verified about them, and how can I compare them?

The current source positions the site as an independent orientation/provider-discovery platform, not a technical cybersecurity contractor. Under that model the provider function is strategically useful. If the owner instead intends to sell their own technical work, business positioning and proof of delivery must be changed deliberately; adding service pages alone does not establish that capacity.

Today /proveedores/ has no profiles. It explains selection criteria and a possible coordination process; it is not yet a usable directory. It potentially serves supplier-selection intent, but an extra page/menu item is not an automatic SEO benefit. Its current title/menu label may create expectations of a list that is absent.

Recommendation: retain /proveedores/ and its existing links, present it as Cómo elegir proveedor until real listings exist, and place that link within the services mega menu/footer rather than giving an empty directory equal top-level prominence. Keep the present header label during this menu-only release; relabeling/moving it is an owner navigation decision, not a technical requirement. Once a useful real directory exists, Proveedores earns a top-level position again.

The provider page should visibly distinguish:
- Current self-service selection advice.
- Real directory status, including when there are no published profiles.
- Any future introduction process, with actual availability and consent.
- Editorial verification, commercial relationships and how to correct facts.
